# The Genesis Pattern — Reproducible Plugin Evolution

> **STATUS: HISTORICAL PROPOSAL — NOT SHIPPED.** The converter instance became
> executable. The signature-engine instance remained a formation proposal: this
> repository ships no `axis_engine.py`, native axis tools, persistent axis state,
> or continuously running signature layer.

The pattern was proposed July 19, 2026 (Codex→plugin) and explored again July
21, 2026 (Memory→signature-engine concept). It records a method for evolving the
plugin by compiling domain requirements in 5QLN and naming a candidate capacity.

## The pattern

```
Domain → Requirements Spec → 5QLN Compiled Surface → Latent Capacity → Plugin Layer
```

### Step 1: Requirements Spec (Breakthrough #1)

Take a domain (Codex, Memory, Design, etc.) and create a formal requirements specification explaining every piece to AI step by step. Model after the Constitutional Requirements Specification format:
- Invariant foundation (the sealed block)
- Domain axioms
- Requirement categories with IDs, priorities, acceptance criteria
- Membrane integrity requirements
- Human source requirements
- Extreme design boundary
- Removal test
- Open decisions deliberately unresolved

### Step 2: 5QLN Compiled Surface (Breakthrough #2)

Convert the requirements into 25 holographic cells using the converter pipeline:
1. Inventory the source → 2. Create manifest scaffold → 3. Build document_cell → 4. Build attestations array → 5. Build 25 cells with formations → 6. Fix traceability → 7. Compile to 0 errors

Each cell carries nested S/G/Q/P/V — semantic operations, not input/process/output labels. The compiler pass proves structural integrity.

### Step 3: Latent Capacity Recognition (Breakthrough #3)

The session that compiled the requirements may expose a candidate capacity. The
original genesis led to the implemented converter. The memory genesis named a
possible signature engine; it did not create or train a persistent axis.

Recognition can make a candidate visible. Naming alone does not make it
operational; executable code, interfaces, tests, and truthful runtime status are
still required.

### Step 4: Build as Plugin Layer

If implemented, integration shape depends on the capacity:
- **Converter:** deterministic tools + skill (session-scoped)
- **Signature engine proposal:** possible tools + skill + persistent axis layer;
  none of these axis components are shipped.

The converter added no new category because tools and skills already existed.
The proposed continuous signature layer remains an unimplemented design option.

## What makes it reproducible

- **The requirements must be genuinely explained to AI** — not copied, not assumed. The act of explaining creates the raw material.
- **The 5QLN compilation must be native** — 25 cells, each carrying semantic S/G/Q/P/V, compiler-verified. Not five headings.
- **The latent capacity is recognized, not designed.** The session has already done the thing. Name what it now knows how to do.
- **Implementation must preserve the candidate's nature without claiming it
  early.** A future layer requires actual executable integration and verification.

## Open question

Both proven instances required the session to perform the act (convert, compile) before recognition. The next threshold: recognition without prior performance.
